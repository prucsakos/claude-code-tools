# Pillars and targets

A pillar is an area of the project to work on. A target is one concrete goal inside a pillar, and each selected target becomes a track. The "Improves" text is the option description in the pillar question, and "Group" is the question the pillar appears in. Each target's bold name is its option label in the target question, and the text after it is the option description.

Every target has a kind. An **optimize** target (the default) improves a metric, so it needs a proxy that a command can measure; a tool the repo lacks can run from a harness under `RUN_DIR/harness/`. A **build** target, marked *(build)*, adds something new and is accepted on acceptance criteria with evidence: new tests, and screenshots for UI. If a selected target has no measurable proxy, or a build target cannot show its evidence, drop it and give the reason in the setup form.

| Group | Pillar | Improves | Targets | Gaming to reject |
|---|---|---|---|---|
| Product | Performance | Speed, memory, size and cost of running the code | **Speed**: wall time of a benchmark, latency, requests per second · **Memory**: peak memory · **Size**: bundle or binary size · **Cost**: API or compute cost per run | caching results across runs, skipping required work |
| Product | UX | How fast and easily a user completes a task | **Page load**: Lighthouse performance score or LCP of key pages · **Task flow**: time or steps of a scripted user flow (e.g. Playwright) · **CLI response**: time to first output | removing steps or features the flow needs, hiding errors instead of fixing them |
| Product | UI | Look, consistency and correctness of the interface | **Consistency**: hard-coded colors, font sizes and spacings outside the design tokens (stylelint count) · **Stability**: layout shift (CLS), visual-regression diff count · **Redesign** *(build)*: a better look and layout for existing screens · **New screens** *(build)*: new screens or components | deleting styles or elements, excluding files from the lint; designs outside the design system (tokens, components), screens that work at only one width or in only one theme |
| Product | Features | New capabilities for the users of the product | **Your features** *(build)*: the features you list in the form · **Proposed features** *(build)*: features the researcher proposes from the code, docs and open TODOs that make users' work much faster or easier | features that do not fit the product's purpose |
| Reach | Accessibility | Use by people with disabilities and with assistive technology | **Violations**: axe or pa11y violation count on key pages; Lighthouse accessibility score | `aria-hidden` or removed elements to silence checks, empty alt text |
| Reach | SEO | How easily search engines find, read and rank the site's pages | **On-page**: Lighthouse SEO score of key pages; pages without a title, meta description or canonical link · **Links**: broken internal links (linkinator, lychee) on a local preview | hidden keyword text, serving crawlers different content, meta text that does not match the page |
| Reach | i18n | Readiness of the interface for translation and other locales | **Strings**: hard-coded user-facing strings (eslint-plugin-i18next or a similar lint); dates and numbers formatted without the locale · **Keys**: missing or unused translation keys (i18next-parser, i18n-unused) | marking strings as not translatable, per-line lint disables, keys with empty or copied translations |
| Engineering | Quality | Correctness of the code | **Tests**: failing or flaky tests · **Types**: type-check error count · **Coverage**: coverage; mutation score | `ts-ignore` / `type: ignore` comments, deleted or assert-free tests, lowered thresholds |
| Engineering | DX | Developer experience: how fast and easily developers build, test and change the project | **Build time**: clean build time (MEASURE_CMD clears the build caches first) · **Test time**: test-suite time · **Install time**: install and first-run time from a fresh clone · **CI time**: CI pipeline time | skipped build or test steps, removed tests, caches kept between measured runs |
| Engineering | OX | Operator experience: deploying, configuring, monitoring and debugging the project in production | **Start-up**: start-up time · **Image size**: container image size · **Log noise**: log lines or errors per smoke-test request · **Config checks**: config errors found at start-up instead of at run time | silenced logs, swallowed errors, removed checks |
| Engineering | Security | Known weaknesses in the code and its dependencies | **Dependencies**: vulnerability count from `npm audit` / `pip-audit` / `cargo audit` · **Code**: Semgrep or CodeQL findings · **Secrets**: secret-scan findings | ignore lists, suppression comments, files excluded from the scan |
| Code health | Code hygiene | Clean code without dead weight or clutter | **Lint**: lint warning count · **Dead code**: dead code and unused exports (knip, vulture) · **Duplication**: jscpd · **Complexity**: radon, eslint `complexity` | rule disables, `noqa` / `eslint-disable` comments, files excluded from the scan, functions split only to lower a per-function score |
| Code health | Dependency health | A small, current and maintained dependency tree (known vulnerabilities belong to Security) | **Unused**: unused dependencies (knip, depcheck, deptry) · **Outdated**: outdated or deprecated packages (`npm outdated`, `pip list --outdated`) · **Footprint**: direct and transitive dependency count; install size | entries in the checker's ignore list, dependency code copied into the repo, removing a dependency the code still needs |
| Code health | Documentation | Docs that exist and are correct | **Docstrings**: docstring coverage (interrogate, eslint-plugin-jsdoc); undocumented public functions · **Doc links**: broken links in the docs (lychee) · **README commands**: README commands that fail | empty or boilerplate docstrings, links removed instead of fixed |

The gaming lists are per pillar. For every optimize target, add the gaming that its metric invites (for LCP: shrinking or removing the largest element).

Build gaming, for every build target: stubs, placeholders or TODOs in place of the feature; hard-coded demo data; tests that do not exercise the new behavior; a feature that no user can reach (no route, command or menu entry); edits to existing tests; changes to existing behavior.

Outdated-package counts and external link checks read the network, so a new release or a slow site can change the value during the run. Prefer an offline proxy when one fits: unused dependencies, dependency count, install size, internal links only.

A pillar or target the user names under "Other" (for example Cost, Reliability, or "CSV export of reports") follows the same rules: write a one-line definition, its kind, a measurable proxy (optimize) or acceptance criteria (build), and its gaming list yourself.

Count metrics (errors, violations, findings) usually give the same value on every run. The setup step detects this and measures them once per side. Count tools usually exit non-zero when they find something, which `measure.sh` reads as FAIL: pipe the tool's JSON output into a counter that prints the count last and exits 0.

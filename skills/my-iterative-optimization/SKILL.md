# Iterative Optimization

This skill defines how a run is orchestrated: who does what, which work runs in parallel, with which time and spend budgets, and who decides what reaches the main branch. It is not only about iterating on a metric: optimizing a metric and building features are two cases of the same orchestration. The four roles below are fixed.

You are the **orchestrator** of a run that works on one or more targets. An optimize target improves a measurable metric; a build target adds new features or designs; a judged target improves work with no metric, accepted on a rubric. You never edit the project's code. You assign work, enforce the time budgets, accept or reject results, keep the user informed, and keep subagent spend low.

## Roles

| Role | How many | Runs when | Writes to |
|---|---|---|---|
| Orchestrator (you) | 1 | the whole run | `RUN_DIR` only: STATE, reference outputs, measurement harnesses |
| Researcher | one per selected pillar | its pillar has fewer queued ideas than experimenters | nothing; sends ideas to you |
| Experimenter | N in total, divided evenly over the pillars | one fresh agent per idea | its own worktree and branch |
| Integrator | 0–1 at a time | you decide a batch is ready (review mode: and the user approved it) | batch worktree, then fast-forwards MAIN |

Files in this skill's directory: `pillars.md` (the pillars and their targets), `researcher-prompt.md`, `experimenter-prompt.md`, `integrator-prompt.md`, and `measure.sh` (the only way anybody measures). `index.sh` combines several component metrics into one index number that a MEASURE_CMD can print (spec format in its header), and `index-check.sh` is its self-check. For each of the three prompt files, fill every `{{…}}` and send the text below its `---` line as the Agent prompt.

## Pillars and targets

A pillar is an area of the project to work on. There are four groups: Product (Performance, UX, UI, Features), Reach (Accessibility, SEO, i18n), Engineering (Quality, DX, OX = operator experience, Security) and Code health (Code hygiene, Dependency health, Documentation). A target is one concrete goal inside a pillar, such as Speed or Memory for Performance. `pillars.md` lists the targets of each pillar, with example metrics and the gaming to reject. These are examples, not a closed list: the user may define pillars and targets freely, of any of the three kinds below.

Every target has one of three kinds:
- **optimize**: improve a measurable metric. An idea is accepted on its measured gain.
- **build**: add something new, such as a feature or a screen. An idea is accepted when it meets acceptance criteria that were fixed before it was dispatched, shown with evidence in the target's evidence form (new tests, screenshots, or `file:line` quotes plus CORRECT_CMD). CORRECT_CMD guards the existing behavior.
- **judged**: improve work that has no command metric and no tests, such as the wording of a thesis, research, or web fact-finding. An idea is accepted on a rubric that was fixed before it was dispatched. The experimenter supplies before/after evidence for each rubric criterion, such as quotes of the old and new text or the sources found. You judge the idea from that evidence; the experimenter never judges its own work. CORRECT_CMD guards the existing behavior.

Each selected target is a **track**. An optimize track has its own metric, MEASURE_CMD, mode, lock setting, R and baseline values. Wherever this skill says "the metric", MEASURE_CMD, mode, lock or R, it means the values of the optimize target in question. A build track has its items, their acceptance criteria, and a cap. A judged track has its rubric. CORRECT_CMD, T_TEST;T_ITER, the run mode and the profile values (N, T_RESEARCH) are shared by all targets. N is divided evenly over the pillars: each pillar gets its own share of the experimenters and its own researcher. Baselines stay numbered per state of MAIN: B0 and every Bk hold one value per optimize target. A run with one target works like a single-metric run.

## Platform rules (Claude Code)

- Subagents run in the background, and a notification wakes you when one finishes. After you dispatch work, end your turn. Do not poll or sleep.
- The Agent tool has no name parameter. Store the `agentId` from every spawn result; SendMessage and TaskStop need it.
- SendMessage to a running agent arrives at its next tool call. It cannot interrupt a running command, so every subagent command has its own timeout.
- Subagents reach you mid-run with SendMessage `to: "main"`. They must load SendMessage with ToolSearch first; the prompt templates say so.
- Timer: Bash with `run_in_background: true` running `sleep <seconds>; echo "TIMER <id>"`. Its exit is a notification. TaskStop cancels it.
- TaskStop stops a background agent or shell by its ID.
- Bash tool: 120 s default timeout, 600 s maximum in the foreground. Run longer measurements with `run_in_background: true`.
- A subagent that waits on its own background command produces an interim notification ("waiting on its own background work"). It has not finished: act only on a notification whose result holds the report block.
- Never `cd` into a worktree in your own shell; use `git -C <dir>` or a `( cd <dir> && … )` subshell. On Windows a directory that is a shell's working directory cannot be removed.
- Run the skill's commands (measure.sh, the timer, `( cd … )` subshells, `'\''` quoting) in the Bash tool, never in PowerShell. On Windows the Bash tool is Git Bash. Do not start `bash` from PowerShell or Python there: it may be WSL's bash, which does not see Windows drive paths like `A:/`. The skill's `.gitattributes` keeps `*.sh` at LF line endings, because bash rejects a CRLF measure.sh with a syntax error.

A pillar defined from scratch gets its targets the same way: propose them from its definition, and the user names others in the reply to the plan.

|---|---|---|
| low | 5 | 3m |
| medium (default) | 10 | 5m |
| high | 15 | 10m |

| Run mode | Who decides what reaches MAIN |
|---|---|
| auto (default) | You. Once the user has confirmed the setup table, you never wait for the user. You accept or reject, batch, migrate and revert on your own, and print one event line after each event (section 4). You shut the run down when nothing is left to do. |
| review | The user approves each batch before the integrator starts (section 3, Review gate). Everything else works as in auto, except that an idle run waits for the user. |

**Confirmation.** The plan is the confirmation layout. First one table with a row per target: pillar, target, kind, metric, build items or rubric, MEASURE_CMD or evidence, lock, and the pillar's experimenters. Show a judged target's whole rubric, criterion by criterion. Show a build target's usage cases next to its evidence, in a few words. A target the user typed appears as they wrote it, with the parts you wrote for it. Below it, the shared values: profile (with N and T_RESEARCH), run mode, the researchers (one per pillar), CORRECT_CMD, EVIDENCE_CMD, pull request, goal. Write every message to the user in the conversation's language, or in the language the user asks for.

After the user confirms:
1. Check that the working tree is clean. If it is not, stop and tell the user. Tell them not to edit the main checkout during the run. Run `git -C REPO switch -c <run branch>`, also with Pull request off. STATE config (step 5) records BASE and the run branch for either value. From here MAIN means the run branch, so the integrator fast-forwards it and BASE stays as it was.
2. Create `RUN_DIR` = `<parent of REPO>/<repo name>.optimize/`. It sits outside the repo, so test runners and linters in MAIN never see the worktrees. `STATE` = `RUN_DIR/state.md`. If the plan showed a leftovers line, carry out its removals now, except those the user kept. Run `git -C REPO worktree remove --force <dir>` per listed worktree, then `git -C REPO worktree prune`, `git -C REPO branch -D <branch>` per branch marked deleted, and `rm -rf RUN_DIR/measure.lock`. If a worktree folder cannot be removed, name it with the reason in the setup summary and go on. If STATE already exists, first move the last run's files into `RUN_DIR/runs/<YYYYMMDD-HHMM>/`: STATE, `patchnote.md`, `shots/`, `ref/`, cleanup scripts and every other top-level entry. Only `harness/`, `wt/`, `runs/` and a kept `measure.lock` stay: the plan reuses the harness commands and paths, and git still tracks the worktrees. The time is the archived run's start time from its config. This way the archives sort by run. An older archive, `RUN_DIR/state-<YYYYMMDD-HHMM>.md`, moves to `RUN_DIR/runs/<YYYYMMDD-HHMM>/state.md` with its own time. An optimize target's `LOCK` = `RUN_DIR/measure.lock` if its lock is on, else `none`. All locked targets share this one path, so their measurements never overlap. Write any harness the plan proposed under `RUN_DIR/harness/`. If CORRECT_CMD reads `RUN_DIR/ref/`, save its reference outputs there again from MAIN, because the last run's copies moved. Everything else you write in RUN_DIR goes under the paths this step names, or under `RUN_DIR/tmp/` for scratch such as ad hoc scripts and logs.
3. Create the measuring worktree: `git -C REPO worktree add --detach RUN_DIR/wt/measure MAIN`, then run SETUP_CMD in it. You measure MAIN only there, never in the main checkout, so measurement output cannot block the integrator's fast-forward. Create one worktree per researcher the same way, `RUN_DIR/wt/researcher-<pillar>` with a slug of the pillar's name (`researcher-code-hygiene`), and run SETUP_CMD in each. Researchers read and profile there, so your checkouts and measurements in `wt/measure` never change files under it. Measure B0 for every optimize target with `measure.sh` (3 runs, T_TEST each), and each guardrail the same way, with its target's lock. Then run CORRECT_CMD. It must pass. This also proves that SETUP_CMD gives a working worktree. If EVIDENCE_CMD is set, run it once in `wt/measure` through `measure.sh` (mode `stdout`, the shared lock) into `RUN_DIR/shots/B0`, and look at the screenshots. Its run time is `ev`. If it fails, drop the UI build targets and say why.
4. Plan the measurements of each optimize target from its B0 median run time `run`. In `stdout` mode `measure.sh` prints no run time: time the whole B0 call and divide by its runs.
   - Lock on: experimenters measure only the candidate and compare it with the current baseline Bk, which you measured under the same lock. No contention is left for an A/B pair to cancel, and the lock time halves. Lock off: experimenters measure base and candidate in their own worktree.
   - S = sides an experimenter measures (1 with the lock on, 2 with it off). L = agents that queue for the shared lock. With the lock on, L = the experimenters of every pillar that has a locked target or a UI build target, plus those pillars' researchers. A UI capture counts as one run, and each researcher makes one locked run per round. With the lock off, L = 1.
   - `R = clamp(min(floor(T_TEST / run), floor(T_ITER / (2 × S × L × run))), 1, 5)`, the runs per side. So R runs fit in T_TEST, and all queued measurements fit in half of T_ITER.
   - All of them wait for the same lock. Use the longest of the locked median runs, and `ev` when a UI build target is selected, for `run` in the second term.
   - If a target's 3 B0 runs give the same value (typical for counts such as lint errors), its metric is deterministic: R = 1, and its spread is 0.
   - If even R = 1 does not fit for some target, lower the experimenters of those pillars until it fits, at least 1 each. It does not fit when 2 × S × L × run > T_ITER, with `run` as in the second term. Give the freed experimenters to the other pillars. N drops only when there is no other pillar. Say so in the setup summary, with the reason.
   - With EVIDENCE_CMD, at most floor(T_ITER / (2 × ev)) experimenters work on UI build items at the same time. This way their captures fit in half of T_ITER even without a locked optimize target. If the UI pillar has nothing else for its other experimenters, give them to the other pillars.
5. Queue the user's build items as ideas, with value high and confidence high; of a split item, queue only its first increment. Write STATE and show the user the setup summary and the empty report. End the setup output with the `Commands:` line of section 2, so the user learns the mid-run commands at the start.

## 2. Event loop

React to events. Update STATE after each one, then print one event line (section 4). Print the full report (section 4) only after a batch reaches MAIN or is reverted, when the user asks for status, and at stop.

| Event | Action |
|---|---|
| A researcher sends an idea | Drop it if it repeats a tried or queued idea, including one that another researcher sent. Drop a build idea that has no acceptance criteria, and a judged idea that has no RUBRIC. A judged idea's RUBRIC applies the target's confirmed rubric to that idea: it may add criteria but never drop one. Otherwise queue it under its target, ranked by score = weight × confidence (high 1, medium 0.6, low 0.3). An optimize idea's weight is its expected relative gain = expected change / base value (120 → 24 s = 0.8; 42 → 0 errors = 1.0). This lets gains in different units compare. A build or judged idea's weight is its value (high 1, medium 0.6, low 0.3). Fill free experimenter slots. An idea that you queue, or drop as a repeat, prints no event line of its own; its researcher's round line lists or counts it. |

- `status`: print the full report (section 4), then one line per running agent: `<role> #<id> <Target>: <m> min left`. A researcher names its pillar and the integrator its batch instead of #id and target. Time left = dispatch time in STATE + the budget the agent was dispatched with − now.

Only these: `T_ITER`, `T_RESEARCH`, a build or judged target's cap (`set cap Features 3`), a pillar's experimenters (`set experimenters UX 2`, which changes the confirmed split). Write the new value to STATE config. For T_ITER or experimenters, also recompute R by setup step 4. It applies from the next dispatch; running agents keep their timers. **Idle check.** After each event, check whether anything is left to do. Nothing is left when the queue is empty, no agent is running, no accepted idea waits, and no researcher can start. No researcher can start when every pillar's research is exhausted or its targets are done. In auto mode, shut down (section 5). In review mode, tell the user once, and wait for stop or new input. A paused run is never idle: it does not shut down until `resume`, `finish` or `stop`.

**Rebalance.** A pillar is idle when all its targets are done, or when its research is exhausted and its queue is empty. Spread the experimenters of idle pillars over the other pillars, within the limits of setup step 4, and say so in the report. When an idle pillar gets ideas again, it gets its confirmed share back as the borrowed experimenters finish.

**Dispatch an experimenter** when a pillar has a free experimenter slot. The pillar's user ideas (source `user`) go first, oldest first. Otherwise pick its idea by the first of these rules that applies, in this order: (1) Target balance: while one of the pillar's targets has queued ideas and no running experimenter, that target's best idea goes; if the target has a queued bold idea and the pillar has none testing, the target's best bold idea goes. This rule wins when it and rule 2 point to different ideas, so that no target waits. (2) Wide search: the score favors safe ideas, so while the pillar has a queued bold idea and none testing, its best bold idea goes. (3) Score: the pillar's queued idea with the highest score. (4) Borrowing: a free slot whose pillar has no queued idea may serve another pillar: the one whose best queued idea has the highest score. It never serves a pillar with a locked target or a UI build target, because their shares set R and the lock budget (setup step 4). The slot serves its own pillar again once the borrowed experimenter has finished. Under every rule, an idea waits while a running experimenter edits its main section (the file and section its TECHNIQUE names), and the next idea by the same rules goes instead, because two experimenters on one section make the later cherry-picks conflict.
1. `git -C REPO worktree add -b opt/<id> RUN_DIR/wt/<id> MAIN`, run SETUP_CMD in it, and record the base SHA.
2. Spawn an agent with `experimenter-prompt.md`, filled with the values of the idea's target, and keep the section of its kind. Include the deadline as a clock time. GAMING = the gaming list of the target's pillar from `pillars.md`, plus the gaming its metric invites (for LCP: shrinking or removing the largest element). For a build idea, add the build gaming list. OTHER_TARGETS = the other selected targets, or `none`.
   - Optimize: with the lock on, BASE_VALUES = the target's runs of the current Bk; with it off, `none`. If MEASURE_CMD contains single quotes, write each as `'\''`. OUTPUT_CHECK = the target's output check, its command and comparison rule, or `none`.
   - Build: ACCEPTANCE = the idea's acceptance criteria. EVIDENCE_FORM = the target's evidence form. For a UI item, SHOTS = `RUN_DIR/shots/<id>`, BEFORE = the screenshots of the current baseline (`RUN_DIR/shots/Bk`) and LOCK = `RUN_DIR/measure.lock`; otherwise SHOTS and BEFORE = `none`.
   - Judged: RUBRIC = the idea's rubric criteria.
3. Start its timer for T_ITER. Record the agentId, timer ID, base SHA and dispatch time in STATE.

**Start a researcher** for a pillar when all of these hold:
- It has fewer queued untested ideas than experimenters.
- Its agent is not running.
- Its research is not exhausted.
- One of its targets is not done.

A pillar whose targets all come from the user's list has no researcher.
1. `git -C RUN_DIR/wt/researcher-<pillar> checkout --detach MAIN`. If MAIN has moved since this worktree's last round, run SETUP_CMD in it.
2. Spawn the agent with `researcher-prompt.md`: its pillar, the other pillars that have a researcher, one TARGETS block per target of its pillar, K = 2 × the pillar's experimenters, and LENS. Give it a deadline of T_RESEARCH. Fill LENS with the pillar's next lens from this list, one per round of the pillar, and record the lens in STATE with the pillar's research status. After the last lens, start again from the first. The lenses fit code, text and research alike:
   1. Remove a whole step instead of making it faster
   2. Invert an assumption the current design makes
   3. Borrow a technique from another field or tool
   4. Change who or what does the work: the user, a tool, an agent, or build time
   5. Make the smallest change to the most-used path: the code, workflow or section used most
3. Start its timer for T_RESEARCH.

**Economy:**
- Run as many experimenters as the split and the queue allow, never more than N.
- Start a pillar's researcher only as in Start a researcher, and ask it for 2 ideas per experimenter of the pillar.
- Never run two integrators.
- Prompts point to STATE for history instead of pasting it.

## 3. Decisions

**Accept or reject: your call.** A result that fails CORRECT_CMD is always rejected. An optimize result with `OUTPUT_DIFF: differs` is rejected as `output changed`, unless the idea's TECHNIQUE names that output change; then decide it by Side effects and direction, below. For every idea, check the scope: `git -C REPO diff <base>..opt/<id>` must not weaken a check, by the rules in experimenter-prompt.md, section "Rules for every change". Those rules allow build, tool and dependency configuration changes that still run the same work; most DX, Performance and Dependency health ideas work that way. A change that drops or narrows a check is gaming. Then compare `git -C REPO diff --stat <base>..opt/<id>` with the files the idea's TECHNIQUE names, and read the diff for changes outside the idea. Decide each change outside the idea by Side effects and direction, below. If the result passes but its PREDICTION failed, inspect it for gaming or an accidental gain before you accept it; if both the prediction and the result failed, record the failed prediction as the reason.

For an optimize idea, also weigh:
- the gain against its own base, compared with the run-to-run spread on both sides;
- the size and risk of the diff against that gain;
- gaming: special-casing the test input, and the GAMING list of the idea's target (for Performance: caching results across runs, skipping required work);
- the other targets: a diff that you expect to make another selected target worse needs a gain that outweighs it.

For a build idea, also weigh:
- every acceptance criterion: its evidence must show that it is met (the evidence the target's evidence form names: new tests that exercise it, or `file:line` quotes; for a UI item, look at the before and after screenshots); a criterion whose evidence cannot be re-checked (no test name, screenshot path or file:line) has no evidence. Re-read each quote on the idea's branch by its text (`git -C REPO grep -n -F '<a distinctive part of the quote>' opt/<id> -- <file>`), or the named test output or screenshot, and judge it yourself; a quote whose text is not in that file on the branch counts as no evidence, and a wrong line number alone does not. In auto mode, accept only when every criterion has evidence;
- the diff does what the idea says and no more, fits the existing architecture and design system, and leaves the existing behavior unchanged;
- gaming: the build gaming list in `pillars.md`;
- the other targets, as for an optimize idea.

New usage cases (build): a report's `NEW_CASE` that is not `none` names an input on which the item or MAIN failed. If that input exists in the repo, append it to its target's usage cases in STATE, marked `#<id>`; otherwise do not add it. Do this whether you accept or reject the idea. When you dispatch a later idea of that target, add one criterion to its ACCEPTANCE per added case: that case behaves no worse than on the idea's base. A case that fails on the base may still fail. Cases are only added, never dropped, and never go into a MEASURE_CMD, because that would break its baseline series.

For a judged idea, also weigh:
- every rubric criterion: its before/after evidence must show that it is met. Judge the evidence yourself, in the judging form of the section 1 Rubric row; do not take the experimenter's verdict. A criterion is met only when the new version wins in both orders. A split counts as within the spread: reject the idea, reason `order split`. Record both verdicts and their agreement per criterion in the decision's evidence in STATE, e.g. shorter: new wins as A and as B, agree. In auto mode, accept only when every rubric criterion has evidence;
- the diff does what the idea says and no more, and leaves the existing behavior unchanged;
- gaming: the GAMING list of the idea's target, and evidence that does not match the diff;
- the other targets, as for an optimize idea.

**Side effects and direction.** Before you accept any result, check its diff against the run's Goal and the constraints recorded in STATE, such as the idea's scope and the orchestration hierarchy. Decide each changed file or behavior outside the idea in this order, even when the result meets its gain or its criteria:
1. The report's SIDE_EFFECTS field does not list it with a reason: reject the idea, reason `unreported side effect`.
2. It is listed, the Goal covers it, and it keeps every recorded constraint, for example a needed change to a neighbor file: it is not a reject by itself. Weigh it like a cost against the gain. A bold idea may need such a side effect.
3. It is listed, but (a) the Goal does not ask for it, or (b) it moves against a recorded constraint: do not accept the result as is. If the in-scope part can stand alone, mark the idea `rejected: side effect <one line>`. Then queue a `narrowed` retest with the same score: the same idea, in-scope part only, plus one acceptance criterion `does not <the side effect>`. An optimize idea has no acceptance criteria: pass the condition in its IDEA text, judge the retest on its measured gain, and check the condition in its diff. If the in-scope part cannot be separated from the side effect, reject the idea.

Record the reason in one line. Remove worktrees with `git -C REPO worktree remove --force <dir>`, because measurement output leaves untracked files. Accepted: remove the worktree and keep the branch. Rejected or failed: remove the worktree and delete the branch.

**Overlapping ideas:** if two accepted ideas change the same code for the same gain, for example two fixes of one hot loop, put only one of them in the batch. Choose the one with the larger measured gain; for build and judged items, the one with the higher score. Mark the other `superseded by #<id>` and delete its branch.

**Batch size: your call.** Aim for the shortest total time to the best MAIN. Each batch costs one integrator run and one re-measure; experimenters keep working meanwhile.
- Migrate early when an accepted idea has a large gain or moves the hot spot. Every later test then runs against the faster baseline, and researchers look at the new hot spots.
- Migrate early when the next increment of a split item waits for an accepted one.
- Collect more when the accepted gains are small, or when running experimenters will soon return ideas for the same code.
- Always migrate when the queue is empty, no experimenter is running and an accepted idea waits.

**Review gate (review mode only).** When you decide a batch is ready, do not start the integrator. Post the proposal. For each item give its id, target, technique, result (measured gain against its base, acceptance results with screenshot paths, or for a judged item its rubric evidence in one line) and diff size (`git diff --stat`). Then list the ideas rejected since the last batch, with their one-line reasons. The user answers `ok`, strikes items (`drop #3`), or names a rejected idea to retest (`retest #6`). Do not ask with AskUserQuestion: it blocks you while timers and agent reports keep arriving. Mark the batch `awaiting approval` in STATE, end your turn, and keep handling events. Ideas accepted in the meantime wait for the next batch.

**Integrator batch:** `git -C REPO worktree add -b opt/batch-<k> RUN_DIR/wt/batch-<k> MAIN`, then run SETUP_CMD in it. Record the pre-batch SHA (`git -C REPO rev-parse MAIN`) in STATE. Spawn `integrator-prompt.md` with the accepted items as ITEMS, one line `<id> opt/<id> <sha>` each (`<sha>` from the experimenter's COMMIT), ordered by measured gain (build and judged items by score). Its timer is T_ITER × (number of items).

**After a batch:** `git -C RUN_DIR/wt/measure checkout --detach MAIN`, then run SETUP_CMD there (the batch may have changed dependencies). Measure every optimize target there → Bk (3 runs per target if all targets' runs together fit in T_ITER, else R), then run CORRECT_CMD there. Measure each held-out input and each guardrail there too, with its target's runs, and record each value next to Bk in STATE. With EVIDENCE_CMD, capture `RUN_DIR/shots/Bk` there the same way as B0.
- Bk is worse than B(k-1) beyond the spread **on any optimize target**, or correctness fails: measure each batch commit on the targets that got worse, in the measuring worktree, then spawn the integrator in revert mode for the commits that made it worse. Create its worktree and record the pre-batch SHA in STATE as in Integrator batch, with `opt/batch-<k>` for the next k. Pass ITEMS as one line `<id> <sha>` per commit, where `<sha>` is the commit in MAIN, newest first. Its timer is T_ITER × (number of items), and on timeout the revert case of the grace-timer row in section 2 applies. Re-queue as `retest` only the ideas its report marks `reverted <sha>`; an idea marked `skipped: conflict` or `skipped: time` keeps its status, because its commit is still in MAIN. Record in STATE each reverted item, its batch, and the target that got worse. With Pull request on, when the revert-mode integrator has finished, push MAIN and update the PR body as in the Pull request paragraph below. This is the check that catches a change that helps its own target and hurts another.
- On a target, Bk gains less than the product of the item ratios: note "overlapping gains" in the report. No other action.
- On a target, Bk beats B(k-1) beyond the spread, but its held-out value does not: within the spread, or worse. Then record `does not generalize` for that batch and target in STATE. Name it in the next full report. No other action.
- On a target, Bk beats B(k-1) beyond the spread, but its guardrail is worse than at B(k-1) beyond the guardrail's spread. Then record `guardrail regressed` for that batch and target in STATE. Name it in the next full report and under "Risks and follow-ups" in the patch note. No other action.

**Pull request (only with it on).** Before every PR create or update, regenerate `RUN_DIR/patchnote.md` from STATE. When you accept an idea, copy its report's `PROBLEM`, `VERIFY` and `RISK` fields into its STATE detail block, because the note is built from STATE. It is a patch note for a reader who reviews the PR, so the reader can judge each item without STATE. The PR can be public: use only what the run produced, never secrets or private data. The note starts with "Summary", above "Review here first": a table with one row per target in STATE config, built from the baselines table and idea rows. Columns: pillar: target, kind, result, and that target's accepted, rejected and reverted counts. Result of an optimize target: `<B0> → <Bk>, spread ±x` with the latest measured Bk, plus `does not generalize` or `guardrail regressed` if STATE recorded it. Result of a build target: its items in MAIN against its cap or list, with their ids. Result of a judged target: its accepted ideas in MAIN, with their ids. Above the batch list, put "Review here first": one line per item in MAIN whose Not verified line is not `none`, with its id and the one claim to check. Also one line per item whose Verify is stamped FAILED or quote not found, with its id and that stamp. If no item has one, write `none` under the heading. Then the note lists the changes batch by batch. Each item in MAIN gets its id, its target, the short SHA of its commit in MAIN, and the files it touches (`git show --stat --format= <sha>`), then five lines. Problem: one line. Change: one line. Result: for an optimize item `<baseline> → <new>, R runs, spread ±x`; for a build item, each acceptance check with its file:line or test; for a judged item, the rubric line and its evidence. An optimize Result ends with its rerun command: MEASURE_CMD on the item's base SHA, then on its SHA in MAIN. Verify: one command or check that a reviewer can rerun. Before each note update, re-run every item's Verify in `RUN_DIR/wt/measure`, checked out at MAIN, so the note shows checks that hold on the PR head. Run a command with a T_TEST limit, then append `passed at <MAIN short SHA>`. If it fails, times out, or prints other than its Verify line claims, append `FAILED at <sha>: <one line>` instead. For a file reference with a quote, find the quote in MAIN and write its current `file:line`; if it is gone, append `quote not found at <sha>`. Take each item's Problem, Verify and risk from its `PROBLEM`, `VERIFY` and `RISK` fields, edited for the reader, instead of writing them from memory at note time. Not verified: the claims in the `NOT_CHECKED` line of its STATE detail block, or `none`. Leave out each claim that you re-checked yourself before you accepted the item; if none is left, write `none`. Then it lists the reverted items with the reason, and the baseline table vs B0. Each Bk row names the SHA of MAIN it measured. Then "Rejected, worth knowing": one line per rejected idea whose PREDICTION failed or whose gain was within the spread, with the idea, its measured number against its base, and the reason. Then "Risks and follow-ups": the `RISK` and side effects that experimenters reported for items in MAIN, and the ideas re-queued as `retest` or `narrowed`. Last, the counts: accepted, rejected, reverted. Under them, one line with the command that lists every experimenter commit of the run: `git log --grep "Optimize-Run: <YYYYMMDD-HHMM>" <run branch>`, with the run's start time. After the re-measure, run `git -C REPO push REMOTE MAIN`. After the first successful push, run `( cd REPO && gh pr create --base BASE --head MAIN --title "<goal>" --body-file RUN_DIR/patchnote.md )`. Store the PR URL in STATE. After later pushes, run `( cd REPO && gh pr edit <PR URL> --body-file RUN_DIR/patchnote.md )`. If a push or a `gh` command fails, tell the user the error and keep testing. The next batch pushes again, and creates the PR if it does not exist yet.

```
| 6 | Performance: Speed | Cache the parsed config | 1.2× | B1: 24.0 → 23.6 s, 1.02×, within spread | — | rejected: within noise |

```

- The first line ends with ` · next result ~<hh:mm>`: the earliest deadline among running experimenters, each one's dispatch time in STATE + the budget it was dispatched with. Omit it when no experimenter runs. Add ` · End <hh:mm>` only when End is set. Then print one Main line per target, with its pillar's current experimenters (and the confirmed share, when a rebalance changed it), and one baseline-table column per optimize target. A build target's Main line counts its items in MAIN against its cap or its list. A judged target's Main line counts its items in MAIN against its cap.
- Est. vs B0 = (its base's gain vs B0 on the item's target) × the item's ratio. It is an estimate until the item is in MAIN; after that, the baseline table holds the measured value. Build and judged items show `—`.
- When a lower-is-better value reaches 0, the ratio is undefined: show the absolute change (42 → 0) instead.
- Statuses: queued → testing → accepted / rejected (reason) / timeout → migrating → in MAIN (Bk) / skipped (reason) / superseded by #id / retest / narrowed.
- In chat, the ideas table of a full report shows only the rows whose status is queued, testing, accepted, migrating, retest or narrowed, plus the rows whose status changed since the previous full report in chat. It ends with one line for the other rows: `+ <n> earlier ideas: <a> in MAIN · <r> rejected · <t> timeout · <s> skipped · <u> superseded (full table in STATE)`, where n = a + r + t + s + u. STATE keeps every row.
- For each optimize target with the lock off, add one line: its absolute values were measured under parallel load, and its ratios are the more reliable figure.
- In review mode, a batch that waits for the user shows on the Main line as `batch <k>: awaiting approval`.

**Catch-up line.** When a user message arrives and at least one event line was printed since the previous user message, start the reply with this one line:

```
Since <hh:mm>: Main B<i> → B<k> · <a> accepted · <r> rejected · <t> timeout · <n> in MAIN · <target>: <old> → <new>
```

`<hh:mm>` is the previous user message's time, and every count covers only the events since then. Add one `<target>` part per optimize target whose value changed; show build and judged targets as `<x> of <cap>`. Then answer the message or command as usual. No line when nothing changed, that is, when no event line was printed since the previous user message. STATE config keeps the time of the last user message: update it on every user message, after the line is built, also when no line is printed.

## 5. State, compaction and stop

STATE holds the config (start time, profile, run mode, every target's values, and with Pull request on REMOTE, BASE, the run branch and the PR URL) and the baselines table. It holds every idea with its target, scope, status, agentId, timer ID, base SHA, branch and SHA in MAIN (the integrator's `applied <sha>`), and each Bk's measured SHA. For each idea it also holds, in one detail block, the TECHNIQUE, EXPECTED, PREDICTION and EVIDENCE as the researcher sent them, and the ACCEPTANCE criteria of a build idea or the rubric of a judged idea verbatim: experimenters and your accept decisions read them from STATE. After each experimenter report, the block gets the result vs its base, R and the spread of each measured side (optimize), and the report's PREDICTION, SIDE_EFFECTS and NOT_CHECKED lines. After your decision, it gets that decision's evidence, short (file:line quotes or rubric evidence), and any reject or revert reason; the section 3 patch note reads them. It also holds each build target's items with the increments still to come and its cap, each judged target's rubric and cap, and the increments still to come of each split idea. It holds each build target's usage cases: those the plan confirmed, and those added from a `NEW_CASE` (section 3), each marked with its idea id. It holds the confirmed and the current experimenter split, and each pillar's research status. It is the source of truth. After a context summary, or whenever you are unsure, re-read STATE before you act.

On stop: TaskStop every running agent and timer. In auto mode, if accepted ideas still wait for migration, run them as one last batch first, unless the stop message says not to. Wait for that batch's integrator report and the re-measure of MAIN. Remove all worktrees and run `git -C REPO worktree prune`. If a worktree folder cannot be removed (on Windows a process may hold it), note it with the reason and go on; do not retry in a loop. Keep the branches of accepted, unmigrated ideas; delete the other `opt/*` branches. Keep the run branch: with Pull request on it is the head of the PR; with it off it holds the result. With Pull request on, also push MAIN once more and update the PR body with the final patch note (section 3). If either fails, name the error in the final report. Name the PR URL in the final report. End the final report with a "Left on disk" block, built from `git -C REPO branch --list 'opt/*'`, the run branch, `git -C REPO worktree list` and the folders you noted. With Pull request on, also build it from `git -C REPO ls-remote --heads REMOTE 'optimize/*'`, which lists the run branches that earlier runs left on REMOTE. Each line names one item and its cleanup command. Per kept branch: its idea id, why it is kept (accepted and unmigrated, PR head, or run result) and `git -C REPO branch -D <branch>`; for the run branch, once BASE has it (PR merged, or merged by hand) or to drop the run, `git -C REPO switch BASE && git -C REPO branch -D <branch>`. With Pull request on, add `REMOTE/<run branch>`, kept as the PR head, and, once the PR is merged or closed, `git -C REPO push REMOTE --delete <branch>`. Each earlier run's branch in that list gets the same kind of line. A forge setting may have deleted the branch already; the command then reports that the remote ref does not exist, which is harmless. Per folder not removed: its path, the reason and `rm -rf <dir> && git -C REPO worktree prune`. Then RUN_DIR: its path, what it holds (STATE, archived STATEs, harness, ref, shots), that the next run reuses it, and `rm -rf <RUN_DIR>`, which also drops that record. Also write the block's commands to `RUN_DIR/cleanup-<YYYYMMDD-HHMM>.sh`, stamped with the stop time. Write it as bash with LF line endings and `set -u` first, one command per item, each after a `# <id or item>: <why kept>` line. Comment out the commands of items kept on purpose: accepted and unmigrated branches and the run branch. Comment out every `push REMOTE --delete` command too, whatever the PR state; its comment line says when to run it, such as after the PR is merged or closed. The RUN_DIR command comes last in the script, also commented out, because it would delete the script and STATE. Write the script but never run it, so the block and the script delete nothing. Print the final report. In review mode, if accepted ideas still wait for migration, offer one last batch.

**Final report.** Build it from STATE after the last re-measure. Print the block below first, then the full report (section 4), and last the "Left on disk" block. Its last line is `bash <script path>`, with the advice to read and edit the script before running it.

```
Run 08:30–12:10 (3h40m) · 4 batches · 9 in MAIN · 14 rejected · 2 timeout
  Performance: Speed       B0 → B4: 120.4 → 9.1 s, 13.2× vs B0 · research exhausted
  Code hygiene: Lint       B0 → B4: 42 → 7, 6.0× vs B0 · stopped
  Features: Proposed       5 of 5 in MAIN · done
  Features: Your features  3 of 5 in MAIN · stopped
Left: #21 #24 accepted, not migrated · 6 queued · Your features: CSV import part 2, filters
Errors: none
PR: https://github.com/<owner>/<repo>/pull/<n>
Next run: proposes again Your features: CSV import part 2, filters
```

- Line 1: the start time from STATE, the time of stop and the duration, the number of batches, and the counts of ideas in MAIN, rejected and `timeout`, by their status in STATE at stop (a `retest` counts as queued).
- One line per target. An optimize target shows B0 → Bk with both values and its ratio vs B0. A build or judged target shows its items in MAIN against its cap or list. Each line ends with its end state, the first that applies: `done` (as in section 2, Integrator finishes); `research exhausted`, when its pillar's research is exhausted and none of its ideas is queued or accepted; else `stopped`.
- `Left:` the ids of the accepted, unmigrated ideas (their branches are under "Left on disk"; do not repeat them), the number of queued ideas, retests included, and per build target or split idea its increments still to come. Write `Left: none` when nothing is left.
- With Pull request on: `Errors:` the failed push or PR update from On stop, with its error, or `none`; `PR:` the URL.
- With Pull request off: `Result:` the run branch, `nothing merged into BASE`, and `git -C REPO switch BASE && git -C REPO merge --ff-only <run branch>`.
- `Next run:` the user's build items not in MAIN, with their increments still to come, which a next run in REPO proposes again (Last run, section 1); `config and targets only` when there are none.

## Common mistakes

| Mistake | Fix |
|---|---|
| Accepting a gain that came from a weaker check | Weakened lint, type-check or audit rules, ignore lists, suppression comments, lowered thresholds and removed tests are gaming: reject. Build config changes that keep the same work are fine. |
| Timing measurements without the lock | Parallel load hides real gains: in testing, a change that saves about 0.4 s per run measured as within noise next to other agents. Keep the lock on in `time` mode. |
| Writing to BASE | MAIN is the run branch, also with Pull request off. The run never checks out, commits to or pushes BASE. |
| Letting the researcher drop or split ideas by its own time estimate | Agents overestimate how long a task takes. The researcher sizes ideas by scope; you split an idea only after it times out. |
| Queuing an idea that another pillar's researcher already sent | Drop ideas that repeat a queued one: Performance and DX can both find the same build-config change. |
